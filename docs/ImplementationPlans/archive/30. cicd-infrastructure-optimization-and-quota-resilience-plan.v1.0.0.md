## 1. Executive Summary & Big-Tech Architectural Context

### 1.1 The Context & The Dilemma

The developer operates RECSY under a **GitHub Student Developer Pack** providing **3,000 free Actions runner minutes per month**. These minutes are a shared resource needed for multiple academic and production projects.

A baseline audit of RECSY's 18 GitHub Actions workflows revealed an alarming consumption profile:

- **Baseline Billed Usage:** **~17,326 billed minutes per month** (over **5.7x** the entire 3,000-minute monthly allowance).
- **Public vs. Private Repository Reality:**
  - RECSY is currently a **Public repository** (`Visibility: public`).
  - Under GitHub's official billing terms, standard Linux (`ubuntu-latest`) Actions runner compute is **100% free and unmetered for public repositories**.
  - Therefore, the user's 3,000 student quota is **not being depleted right now** by RECSY.
  - **However**, if RECSY is ever switched to **Private** (for proprietary IP, commercialization, or private user data), this repository would completely incinerate the entire 3,000-minute monthly quota in **under 5.2 days**.
  - Even on public repositories, running 17,326 minutes across sub-hourly crons triggers GitHub account-level concurrency limits (20 concurrent jobs max), causes runner queue starvation, pollutes the Actions history (over 1,969 runs recorded), and hits chronic cron scheduling jitter.

### 1.2 The Core Question: Was This Deliberate Engineering or a Massive Mistake?

Through exhaustive code analysis, commit archaeology, and review of ADRs 0014, 0015, 0017, 0019, 0021, and Master Plans 25 & 29, the answer is clear:

1. **The Intent was 100% Deliberate and Well-Reasoned:**
   - The system was designed to adhere to enterprise-grade specifications (Plan 25: Multi-User Platform, Quotas, Billing and Monitoring).
   - High-frequency tasks (`ops-alerts` at 5m, `metering-maintenance` at 15m, `billing-reconcile` at 30m) were specified to meet strict production SLOs: 5-minute detection of stuck query leases, 15-minute lease token release, and 30-minute Stripe webhook auto-healing.
   - Paced tasks (`scorecard-auto` 4x/day, `source-watch` 4x/day) were deliberately engineered as **rate-paced queue consumers** to operate sustainably under **Google AI Studio Free Tier API limits** (5 RPM, 20–50 RPD per key across 6 rotating keys).
2. **The Execution Platform was an Architectural Mismatch (Anti-Pattern):**
   - In big tech (Google, Meta, AWS), sub-hourly background tasks run on **persistent daemon containers** (Kubernetes CronJobs, Celery workers, Borg tasks) where execution is zero-cold-start and sub-second.
   - Translating sub-hourly requirements into **GitHub Actions scheduled runners** creates an extreme mismatch:
     - **Billing Granularity:** GitHub rounds _every single job execution up to the nearest whole integer minute_. A 16-second SQL query costs 1 full minute.
     - **Secrets Gate Overhead:** To prevent failed runs on forks, each workflow runs a separate `secrets-gate` job. 5 seconds of secrets check + 16 seconds of work = **2 billed minutes** per run.
     - **Cron Jitter:** GitHub Actions crons are best-effort; during peak hours, jobs are routinely queued and delayed by 15 to 45 minutes, rendering a 5-minute alert check ineffective.
     - **Redundant Shard Spin-Up:** Workflows like `ingest-resume` spin up 4 parallel runner shards daily even when zero phones require quota resumption.

## 2. Multi-Perspective Architectural Deep-Dive

### 2.1 Perspective 1: Staff CI/CD Infrastructure Engineer

_Focus: Runner lifecycle economics, billing mechanics, container overhead, queuing, and artifact caching._

```
GitHub Actions Runner Cost Model:
Total Billed Minutes = SUM_over_jobs( ceil( duration_seconds / 60 ) * runner_os_multiplier )
For Linux (ubuntu-latest): multiplier = 1.0.
```

1. **The Sub-Minute Rounding Trap:**
   - `ops-alerts.yml` runs every 5 minutes (288 runs/day = 8,640 runs/month).
   - Execution duration: 16.0 seconds.
   - Billed duration: 1.0 minute per job.
   - Total wasted compute ratio: **3.75x** (only 16s of CPU used for every 60s billed).
   - Result: **8,640 billed minutes/month** for a lightweight health check.
2. **The Missing Cache Penalty:**
   - In `scorecard-auto.yml` and `ingest-resume.yml`, `actions/setup-node@v4` is executed **without** `cache: 'pnpm'`.
   - Every single run performs a fresh download of npm dependencies, adding 25–45 seconds of network I/O per job.
3. **The Unconditioned Matrix Flaw:**
   - `ingest-resume.yml` defines a static 4-job matrix (`shard: [0, 1, 2, 3]`).
   - In 85% of nightly runs, zero phones failed from quota exhaustion. Yet GitHub Actions provisions 4 separate Ubuntu VMs, installs Node, pnpm, Python 3.12, and pip packages (`yt-dlp`, `youtube-transcript-api`), only for each shard to discover an empty work queue.
4. **Trigger Leakage on Documentation & Keepalive:**
   - `ci.yml` and `db-tests.yml` listen to `push: branches: [master, main]` without `paths-ignore`.
   - Every Sunday at 00:00 UTC, `keepalive.yml` commits `.github/KEEPALIVE.txt` to master. This harmless commit triggers full CI and database integration suites (~7.5 billed minutes).

### 2.2 Perspective 2: Senior Principal Backend & Distributed Systems Engineer

_Focus: Data integrity, idempotency, event-driven vs. polling, database connection exhaustion, and self-healing systems._

1. **Lazy vs. Eager Expiration (`metering-maintenance`):**
   - ADR 0019 established atomic, two-phase metering leases (`query_leases`).
   - The database function `recsy_reserve_query()` already validates lease expiration **lazily on read/write** for each subject.
   - A stuck `reserved` lease does _not_ corrupt user quotas permanently; it simply locks in-flight concurrency slots until swept.
   - Sweeping expired leases every 15 minutes is unnecessary for current traffic volumes. A single nightly sweep (or hourly at most) maintains database hygiene without operational degradation.
2. **Stripe Webhook Inbox Truth (`billing-reconcile`):**
   - ADR 0021 established an idempotent webhook inbox (`billing_events`) with cryptographic signature verification.
   - Stripe delivers webhooks in real-time with automatic retries (up to 3 days with exponential backoff).
   - `billing-reconcile.ts` is purely a **secondary reconciliation safety net** for disaster recovery (e.g. prolonged server outage or dropped webhook delivery).
   - In financial infrastructure, batch reconciliation is standardly scheduled as an **End-of-Day (EOD)** or **Twice-Daily** batch job. Running it every 30 minutes on an unlaunched/low-volume platform burns compute with zero added reliability.
3. **Ops Alerting Inversion (`ops-alerts`):**
   - `ops-alerts.ts` runs SQL queries against Postgres to detect stuck leases, high refund ratios, and unhandled webhooks.
   - As Plan 25 Section 13.4 explicitly admits: _"A database-driven alerter cannot report a database outage."_
   - Furthermore, Plan 25 states: _"The SLO checks that matter most are also evaluated inside `/internal/usage` on load."_
   - Running an internal SQL poller on GitHub Actions every 5 minutes violates observability principles. Outages must be monitored externally (via ping/synthetic HTTP probes on `/api/health`), while deep database integrity can be checked daily or on internal dashboard access.

### 2.3 Perspective 3: Staff AI & LLM Systems Engineer

_Focus: Google AI Studio rate limits, key rotation pools, quota replenishment cycles, and staleness guards._

1. **The Free-Tier Rate Constraint Matrix:**
   - Google AI Studio Free Tier operates under strict limits:
     - **RPM:** 5 Requests Per Minute (or 15 RPM on older tiers).
     - **TPM:** 250,000 Tokens Per Minute.
     - **RPD:** 20 to 50 Requests Per Day per project/key.
   - RECSY configures up to 6 distinct project keys (`GEMINI_API_KEY` through `GEMINI_API_KEY_6`).
   - With 6 keys at 20 RPD, total daily capacity across the pool is **~120 structured LLM requests/day**.
2. **Scorecard Economics:**
   - 1 smartphone evaluation requires **7 aspect evaluations** (`camera`, `battery`, `display`, `performance`, `design`, `audio`, `value`).
   - Each aspect requires 1 structured LLM call with a 4.5s rate-pacing delay (`aspectDelayMs: 4500`).
   - 1 phone = 7 LLM calls.
   - Therefore, a daily budget of 120 calls can score at most **~17 phones per day**.
3. **Why `scorecard-auto` was scheduled 4x/day (The Intent):**
   - If `scorecard-auto` ran only once a day with a batch limit of 20 phones, it would immediately exhaust the daily RPD of active keys, encounter a 429 quota error, and exit.
   - When quota exhaustion occurs (`isScorecardQuotaExhaustedError`), the script exits cleanly with code 0 and leaves remaining phones due in the database (`next_scorecard_at <= now()`).
   - The 6-hour interval (`04:17, 10:17, 16:17, 22:17 UTC`) was selected to **spread consumption across four windows**, aligning with quota replenishments (which Google AI Studio often calculates on rolling or timezone-dependent windows) and key rotation failovers.
4. **The Staleness Guard (The Optimization Enabler):**
   - ADR 0015 and Plan 29 built MD5 chunk fingerprinting (`computeChunkFingerprint(db, phone.id)`).
   - If no new review chunks have been ingested for a phone, `lastScorecardFingerprint === chunkFingerprint`.
   - The phone is skipped **instantly with 0 LLM calls**.
   - **Crucial Insight:** Running 2 times a day (every 12 hours) instead of 4 times a day preserves the multi-window retry capability for quota replenishment while immediately cutting runner execution by 50%!

### 2.4 Perspective 4: Product Owner & Recommendation Quality Guardian

_Focus: Editorial trust, ground-truth consensus, freshness tiers, and consumer value._

1. **Phone Review Velocity in the Real World:**
   - Smartphones are announced at events (Apple September, Samsung January/July, Google October).
   - Comprehensive reviews (MKBHD, Mrwhosetheboss, GSMArena, The Verge) drop during an initial 7-day embargo window, followed by 6-month and 1-year long-term reviews.
   - Reviews do **not** publish continuously every 6 hours. Tech creators publish at most 1–2 videos/articles per day.
2. **Freshness Invariant Verification:**
   - `hot` tier phones (launched <= 60 days): Ingested on a 3.5-day cycle.
   - `warm` tier phones: Ingested Mon/Wed/Fri.
   - `cold` tier phones: Ingested Sundays.
   - If `source-watch` and `creator-watch` scout candidate links twice a day (every 12 hours) instead of four times a day, **zero candidate reviews are lost or delayed**, because tiered ingestion runs only once daily at 02:17 UTC.
   - All staged links are cleanly swept and ingested in the exact same nightly pass!

## 5. Architectural Pre-Mortem: Failure Modes & Mitigations

We rigorously stress-tested this optimization plan against 6 potential failure modes:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                PRE-MORTEM STRESS TEST                                  │
└────────────────────────────────────────────────────────────────────────────────────────┘
  1. Flagship Phone Launch Embargo (0-Day Reviews)
     Issue: Apple announces iPhone at 17:00 UTC. Reviews publish at 18:00 UTC.
     Risk: Will reducing source-watch to 2x/day delay review ingestion?
     Mitigation: The 01:23 UTC scout runs before the 02:17 UTC tiered ingest. The review is
     ingested in that night's batch. Time-to-recommendation remains < 12 hours. Operators
     can also trigger manual instant scout via workflow_dispatch.

  2. Mid-Run Gemini Quota Exhaustion (429 / RESOURCE_EXHAUSTED)
     Issue: Nightly ingest hits Gemini quota on phone 3 of 10.
     Risk: Will reducing scorecard-auto to 2x/day cause phones to stay unscored?
     Mitigation: Scorecard agent has built-in retry-safety (ADR 0015). Failed phones are
     never rescheduled (next_scorecard_at remains in past). The 16:17 UTC run (12h later)
     picks up the pending phones cleanly with fresh daily quota.

  3. Transient Stripe Webhook Delivery Failure
     Issue: Network glitch between Stripe and Supabase during user checkout.
     Risk: With billing-reconcile running daily instead of every 30m, is credit delayed?
     Mitigation: Stripe automatically retries failed webhooks at 1h, 2h, 4h, and 8h intervals.
     Client return page (/account/billing?success=true) performs instant interactive
     fulfillment from session ID. Daily reconciliation acts as a tertiary backstop.

  4. Ingestion Resume Pre-Flight Gate False Negative
     Issue: Ingest run failed but error was recorded in memory, not in ingest_runs table.
     Risk: Pre-flight check sees 0 failed rows and skips resume job.
     Mitigation: Plan 17 (drizzle/migrations/0004_equal_sauron.sql) already made per-source
     failure logging durable. The pre-flight check inspects both ingest_runs.error_stage
     and phones.next_ingest_at <= now() for incomplete phones.

  5. Database Connection Spike During Daily Alignment
     Issue: ops-alerts, metering-maintenance, and billing-reconcile all running in parallel.
     Risk: Exceeding Supabase transaction connection pool limits (Direct vs. PgBouncer).
     Mitigation: Stagger cron start times deliberately:
       - 04:00 UTC: ops-alerts
       - 04:30 UTC: metering-maintenance
       - 05:00 UTC: billing-reconcile
     Zero connection pool overlap.

  6. GitHub Actions Cron Queue Jitter
     Issue: High global Actions traffic at top of the hour (e.g. 04:00:00).
     Risk: Workflows delayed or starved.
     Mitigation: Use non-zero prime/offset minute values across all schedules:
       - 04:17 UTC, 16:17 UTC (scorecard)
       - 01:23 UTC, 13:23 UTC (source-watch)
       - 02:17 UTC (ingest-tiered)
       - 03:20 UTC (ingest-resume)
     Avoiding ':00' and ':30' eliminates 90% of GitHub Actions scheduling queue delay.
```
