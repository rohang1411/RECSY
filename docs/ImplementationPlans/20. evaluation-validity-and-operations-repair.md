# RECSY evaluation validity and operations repair

Status: Evaluation integrity and bounded component diagnostics implemented and checked on 2026-10-05; benchmark validity, product-path repair, and production-readiness gates remain open. This is an acceptance record for this checkout, not a product-quality claim.

## Objective and evidence boundary

Make `/internal/eval` and the CLI reproducible ways to measure _specified components_ of RECSY. Every displayed result must identify its dataset, catalog, code revision, provider, sample/failure counts, and measurement boundary. A synthetic fixture or deterministic provider is a functional test, not evidence of live-model quality. No numerical outcome enters a resume until a recorded run and its evidence have been reviewed.

The historical numbers and labels in `RECSY_V2_PROJECT_CONTEXT.md` are claims about prior work, not validated current outcomes. The 2026-10-03 review in `docs/Reviews/01_RECSY_Metric_Verification_ChatGPT.md` is useful but partly stale: current code already uses binary checked-slot JGA, counts empty recommendations as a failure, uses one Q&A retrieval, and computes refine F1. Re-audit the live code before accepting each item.

## Baseline faults identified before repair

- `fixtures/eval/golden-benchmark-dataset.json`: 30 synthetic recommendation personas and 20 Q&A cases; `multi-turn-trajectories.json`: 15 trajectories and 37 turns. These are authored fixtures, not independently adjudicated relevance or factual ground truth.
- Recommender NDCG derives grades with production ranker helpers and the same catalog signals. Label it **MAUT/ranker agreement**, never independent recommendation quality. Product returns three picks; NDCG@5 is outside that contract.
- Q&A citation checks use word overlap and loose numeric matching. They cannot establish ALCE semantic entailment, claim truth, or fully supported answer rate. The actual generation retrieval is available and should be the evidence source.
- The baseline orchestrator defaulted to a deterministic provider even when a suite or tier implied an LLM; the retrieval path needed explicit provider injection. Historical token/cost figures included hardcoded or pricing assumptions. Explicit tracks and provider-usage coverage now replace these assumptions.
- Baseline load stress measured retrieval or in-memory ranking, not full HTTP/product capacity; empty catalog could turn retrieval into a successful no-op; pool saturation was arithmetic, not telemetry; worker failures were swallowed. The repaired probe fails on missing data and reports completed-attempt diagnostics, but HTTP capacity remains unmeasured.
- The baseline portal's fixed target badges, zero-filled cost, stale fixture count, and generic error toast could mislead. The repaired portal displays observed counts and errors. A database ping established connectivity only.

## Work sequence and acceptance gates

### P0 — provenance, preflight, and honest presentation

1. Validate fixture schemas, unique IDs, turn order, nonempty arrays, reference-fact presence, numeric thresholds, and corpus prerequisites before writing a run. Compute SHA-256 hashes of loaded fixture bytes. Reject incompatible datasets with a file/case/path-specific error. Audit that fixture phone slugs and usable corpus exist for the selected suite; fail or show explicit coverage, never silently omit cases.
2. Require an explicit `stub` or `live` provider selection for LLM suites. Record provider and model identity for extraction, embeddings, and generation; pass the same selected provider into all paths. For live runs, require configured credentials. Keep stub runs clearly labeled and ineligible for model-quality claims.
3. Persist run metadata: commit hash, fixture hashes/counts, catalog size/snapshot fingerprint, provider selection, region, selected sample, timestamps, and component boundary. Preserve failure details and stage (preflight, catalog, retrieval, generation, metric, persistence). A suite completing with failures or warnings cannot be shown as an all-pass run.
4. Show preflight failures, selected track, effective sample sizes, and precise per-case errors in the portal and CLI. Remove fabricated targets, fake zero cost, and labels that imply semantic verification or full-system capacity. Export the same metadata and errors.

### P1 — metric correctness

5. Keep binary checked-slot JGA distinct from slot accuracy; explicitly state that missing unannotated slots are not checked. Make expected negative/empty slots checkable. Count retention only on eligible, independently expected slots; never give an unchecked turn credit. Count resets only when all specified prior state is examined. Report numerator and denominator.
6. Use independent persona constraints to test returned picks, including missing price and empty output. Keep MAUT as consistency and add an independent, adjudicated relevance file before publishing a quality NDCG. Validate catalog coverage of all adjudicated slugs and freeze catalog/version. Remove NDCG@5 and unsupported “optimal” thresholds for the three-result contract.
7. Separate citation-ID validity, lexical evidence overlap, numeric string checks, abstention heuristics, and human/NLI-supported attribution. Rename or suppress any purported ALCE/FSAR semantic scores until validated against independently adjudicated claim/evidence labels. Include failed and unavailable cases in coverage denominators. Ensure the evaluator uses exactly the chunks shown to generation.
8. Never infer API cost from guessed tokens or a fixed price. Show measured provider usage only when complete for every eligible call, alongside a coverage count. Price estimates require a dated, explicit price table and model match; otherwise omit them.

### P2 — load and diagnosis

9. Fail preflight if the selected component has no data. Validate positive workload/concurrency bounds; count outcomes from actual completed attempts, retain error class/message and latency for failures, and use successful requests for goodput. Remove synthetic pool utilization. Separate setup/warmup from timed measurements; report catalog/chunk counts, cache state, concurrency, duration, p50/p95/p99 with sample count.
10. Add a bounded HTTP end-to-end test for the actual recommendation and Q&A routes in a controlled environment, with live-provider cost and quota controls. Measure stage spans (DB, extraction, ranking, retrieval, generation, persistence), failure causes, and sustained arrival rate; no capacity claim until this exists and has run against a stated environment. Keep component benchmarks separately labeled.

### P3 — benchmark quality and readiness

11. Build a held-out benchmark with independently reviewed shopper constraints, phone relevance judgments, source passages, expected answer facts and abstentions. Double adjudicate a sample, retain disagreement and resolution, freeze hashes, and prevent prompts/code tuning against this test set. Synthetic cases stay as development regression tests. No dataset can be certified “perfect”; document known limitations and coverage.
12. Add abuse/fault cases: prompt injection, missing or stale source, contradictory evidence, price/currency drift, impossible constraints, resets, provider 429/timeouts, DB failures, and duplicate/concurrent runs. Require failure localization and readable remediation in the portal.
13. Run static checks, unit/counterexample tests, API integration tests, controlled live-model runs, and a bounded load sweep. Record raw artifacts and exact environment. Review SLOs, security, quotas, observability, backups, migration/rollback, deployment and incident behavior before a production-readiness decision.

## Resume release rule

Only quote metrics from a stored, exported, independently inspectable run. State the exact boundary (“in-memory ranking”, “DB retrieval”, “live recommendation API”), dataset source and size, catalog snapshot, provider/model, measured numerator/denominator and uncertainty when meaningful. Exclude stub, synthetic-only, incomplete-coverage, self-labeled ranking, or lexical-citation figures from product-quality claims. “Production ready” requires the P3 readiness evidence, not a passing benchmark suite.
