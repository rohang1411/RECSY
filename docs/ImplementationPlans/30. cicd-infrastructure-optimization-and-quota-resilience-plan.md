## 1. Executive summary

### 1.1 The honest picture

v1.0.0 sets out to cut Actions minutes by 92 percent, so that RECSY would fit inside the 3,000 free minutes of the GitHub Student Pack if the repository ever went private. The goal is reasonable. The plan as written would not achieve it and would break or degrade several things on the way. The eight findings that matter most, in order of damage:

1. **The baseline is arithmetic, not measurement.** The 17,326 min/month figure is nominal cron frequency times one minute. The run history shows GitHub delivers these schedules far less often than nominal: `Ops Alerts Sweep` is on run number 100 in total, and the last four scheduled runs were 03:48, 11:55, 19:47 and 00:44 UTC, not every 5 minutes [RUNS]. The repository is public, so billed minutes today are zero [RUNS: repository search shows `visibility: public`]. The savings claims, and all "minutes saved" rows, are unsupported until WP-00 measures real usage.
2. **`cache: pnpm` as written breaks jobs.** In 10 workflows `actions/setup-node` runs before `pnpm/action-setup`. `setup-node` with `cache: pnpm` calls `pnpm store path` at that step and fails when pnpm is not yet installed. v1.0.0 asks for exactly this change in `scorecard-auto.yml` and `ingest-resume.yml` [CODE].
3. **The `ingest-resume` gate would remove real ingestion work.** v1.0.0 assumes the job only retries quota failures and queries a column (`error_stage`, `created_at`) that does not exist on `ingest_runs`. In fact `ingest-auto --resume-failed` also consumes the due `crawl_queue`, and when there is nothing to resume it falls back to a normal ingestion pass over all tiers. The latest scheduled resume run took 27 minutes while the tiered run took 1.5 minutes [CODE, RUNS]. Gating on "no failed rows" would silently stop that work.
4. **`ops-alerts` at daily cadence goes blind.** Four of its ten rules look only at the last 10, 30 or 60 minutes (`refund_ratio`, `late_commit`, `dispute_opened`, `anon_ip_spike`). Run once a day, they inspect the few minutes before 04:00 UTC and nothing else. v1.0.0 says it "preserves all 6 alert rules"; there are 10 [CODE].
5. **The daily order makes `ops-alerts` fail every day.** v1.0.0 runs `ops-alerts` at 04:00 and the lease sweep at 04:30. `lease_leak` pages when any lease is more than 5 minutes past expiry, and only the sweep clears it. Any lease leaked in the previous 24 hours therefore pages the next morning, and the workflow exits 1 [CODE].
6. **`paths-ignore` on `ci.yml` can make PRs unmergeable.** `ci-success` is the documented required status check. A workflow skipped by `paths-ignore` never reports it, so a docs-only PR waits forever. It also lets unformatted Markdown into `master` because `pnpm format:check` is `prettier --check .` and covers `docs/` [CODE]. The keepalive justification is wrong: the heartbeat commit carries `[skip ci]` and is pushed with `GITHUB_TOKEN`, which does not trigger workflows at all.
7. **Clock-based ordering does not hold.** v1.0.0 relies on "scout at 01:23, ingest at 02:17" and "scorecard right after ingestion". On 2026-11-12 the 02:17 ingest actually started at 09:56 (7 h 39 min late), the 03:20 resume at 11:28 and the 04:17 scorecards were 2 to 6 hours late [RUNS]. Any ordering the pipeline needs must be explicit, not encoded in cron minutes.
8. **Half of the scheduled workflows were failing before today.** The ops-alerts, billing-reconcile, metering-maintenance, abuse-detect, account-maintenance and catalog-images runs in the last 24 hours before PR #82 all failed; the first scheduled run after the merge (metering-maintenance 03:15 UTC) passed [RUNS]. The 5-minute alerting SLO was not operating at all. A cadence plan built on that period's data is meaningless.

### 1.2 What v2.0.0 does instead

- **Measure first (WP-00).** A repeatable usage report replaces the invented baseline. Cadence decisions use it.
- **Do the changes that cost nothing in fidelity (WP-01, WP-02).** Correct pnpm caching (with the required ordering), one job instead of two per gated scheduled workflow, a real concurrency group for resume, and a guard test that stops these mistakes coming back. These alone remove about half the billed minutes of every small scheduled workflow, with no change to what runs or when.
- **Change cadence only where the plan can show nothing is lost (WP-03 to WP-05).** `ops-alerts` goes to every 4 hours with alert windows scaled to the cadence, and the lease sweep runs inside it, before the alerts. Billing reconciliation goes to every 6 hours while Stripe is live. `creator-watch` is retired as a schedule because `source-watch` already contains it. Scorecards stay at 4 runs a day.
- **Gate `ingest-resume` correctly (WP-04)** by reusing the real selection code, counting all three work sources, and treating the fallback pass as an explicit owner decision.
- **Defer the CI path filter (WP-06)** and, if done, do it inside the workflow so the required check always reports.
- **Fix documentation and SLO drift (WP-07)** because Plan 25 and 12 runbooks state 5, 15 and 30 minute targets that this plan changes.
- **Optional: move the sweep to `pg_cron` (WP-08)** which gives the original 15-minute fidelity for zero Actions minutes.

### 2.2 Design errors in v1.0.0

1. **Cost goal and quality invariant were not reconciled.** The document states a zero-degradation invariant and then cuts every cadence. Each cut needed an argument that nothing is lost. The arguments for `ops-alerts`, `ingest-resume` and `scorecard-auto` fail (Section 2.1).
2. **No acceptance criteria and no rollback.** WP-5 was "verify zero regression on live repo tests". There is no per-WP test, no dry run, no revert plan.
3. **Cadence cuts for an unmet SLO were framed as savings.** The 5 minute, 15 minute and 30 minute targets are in Plan 25 and in runbooks. They were not met before this plan (GitHub delivered every 4 to 8 hours), and changing them needs an explicit amendment (O7).
4. **Cross-workflow dependencies were never listed.** Scouts feed the `crawl_queue`; the queue is consumed by both `ingest-tiered` and `ingest-resume`; both consume Gemini quota that `scorecard-auto` also uses; `ops-alerts` evaluates what `metering-maintenance` repairs. None of these edges is in v1.0.0.
5. **No guard against recurrence.** Nothing stops the next change from reintroducing a `cache: pnpm` ordering bug or a missing secrets gate.

### 2.3 What v1.0.0 got right and v2.0.0 keeps

- The sub-minute rounding trap and the doubled billing from the separate `secrets-gate` job (C3). v2.0.0 fixes the real cause in WP-02.
- Daily retention for `ingest-tiered`, `catalog-refresh`, `abuse-detect`, `account-maintenance` (unchanged).
- Staggered start minutes off `:00`.
- `ingest-resume` should not spend four runners on an empty queue (done correctly in WP-04).
- The idea that the scout is metadata-only and cheap (it is: `source-watch` scans 36 channels and 10 feeds in about 24 seconds [CODE]).

## 4. Architecture decisions

### D30-1 Measure, then cut

Every cadence change is justified by a measured number from WP-00, not by cron arithmetic. The acceptance criterion for the whole plan is relative: the measured billed minutes per month, computed as if the repository were private, after the plan are lower than before, with no regression on the invariant below.

### D30-2 Fidelity-neutral changes first

Changes that cost nothing in behavior (cache, job merging, concurrency, guard test) ship first and alone. They deliver most of the safe saving. Cadence changes that alter alert latency, scout latency or scoring latency are separate WPs with owner gates.

### D30-3 One job per gated scheduled workflow

Replace the `secrets-gate` job plus real job by a single job whose first step probes the secrets and whose other steps carry `if: steps.gate.outputs.configured == 'true'`. This keeps the "skip on forks and unset secrets" behavior and halves billed minutes for every non-matrix scheduled workflow. Matrix workflows keep a gate job, but that job also does the useful pre-flight work (D30-5).

### D30-4 Ordering is explicit, never by clock

If one workflow needs another to have finished, the plan expresses it with `workflow_run` or by putting both pieces of work in one job. Cron minutes are only for spreading load. For this plan the only hard edge is "sweep leases before evaluating alerts", solved by running the sweep as the first step of the alerts job.

### D30-5 A gate reuses production selection code

A pre-flight that decides whether work exists must call the same function the worker calls (`pickResumePhones`, `pickQueuedCrawlItems`), not a re-written SQL query. Otherwise the gate and the worker drift apart.

### D30-6 Alert rules become cadence-independent

Windowed rules take their window from the alerting cadence (`ALERT_WINDOW_MINUTES`, default 15) instead of hard-coded constants, and thresholds are expressed per window. This is the only way a 4 hour cadence keeps the 30 minute and 1 hour rules meaningful.

### D30-7 Required checks are never path-filtered at the trigger

If CI gets a lighter lane for docs-only changes, the filtering happens inside the workflow so `CI / CI success (required)` always reports.

### D30-8 Guard test for workflow invariants

A unit test parses every workflow file and fails the build if: `cache: pnpm` is used before `pnpm/action-setup`; a scheduled workflow has no secrets probe; `ci.yml` has a trigger-level `paths`/`paths-ignore`; a `concurrency.group` of a scheduled workflow contains `run_id`; a cron expression is not parseable.

### 5.3 Gemini quota day

Google AI Studio free-tier daily request limits reset at **midnight Pacific time**, which is 08:00 UTC in winter and 07:00 UTC in summer [VENDOR, VERIFY against the dashboard before relying on it]. The current Gemini consumers fall in these quota days:

## 7. Cost model

### 7.1 Method

Billed minutes per month, as if the repository were private, with Linux runners at multiplier 1:

`sum over scheduled runs of sum over jobs of ceil(job_seconds / 60)`.

Public repositories are free today. The scheduled run count to use is the **delivered** count from WP-00, not the nominal one. For a private repository GitHub's delivery of schedules may differ from the public case [VERIFY]; the nominal count is an upper bound.

## 9. Verification, rollout and rollback

### 9.1 Merge order

4. WP-06 only if WP-00 justifies it. WP-07 after WP-03 to WP-05. WP-08 only on owner decision.

### 9.2 Tooling

- `actionlint` on every touched workflow, run in the PR. [VERIFY which install path the owner prefers; it is a Go binary and is not currently a dependency.]
- The guard test (`test/infra/workflows.test.ts`) in the normal `pnpm test` lane.
- `gh workflow run <file> --ref <branch>` for dispatch runs; log the run URLs in the PR.

### 9.3 Rollback matrix

| :---------------------- | :---------------------------------------------------------------- | :------ | :----------- |

### 9.4 Failure handling during rollout

If any touched workflow fails twice in a row after a merge, revert that WP first, then diagnose. Do not patch forward under a failing production schedule. Never disable a workflow in the Actions UI as a fix (it also disables its manual runs and is easily forgotten).

### Appendix A: single-job gate pattern (WP-02)

```yaml
jobs:
  sweep:
    name: Evaluate Operations Alert Rules
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - id: gate
        name: Check pipeline secrets
        shell: bash
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: |
          if [ -n "$DATABASE_URL" ]; then
            echo "configured=true" >> "$GITHUB_OUTPUT"
          else
            echo "configured=false" >> "$GITHUB_OUTPUT"
            echo "DATABASE_URL not configured — skipping ops alerts sweep."
          fi

      - uses: actions/checkout@v4
        if: steps.gate.outputs.configured == 'true'

      - uses: pnpm/action-setup@v4
        if: steps.gate.outputs.configured == 'true'

      - uses: actions/setup-node@v4
        if: steps.gate.outputs.configured == 'true'
        with:
          node-version: 22
          cache: pnpm

      - name: Install dependencies
        if: steps.gate.outputs.configured == 'true'
        run: pnpm install --frozen-lockfile

      - name: Run ops alerts
        if: steps.gate.outputs.configured == 'true'
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: pnpm exec tsx scripts/ops-alerts.ts
```

The `env` block of the real step stays exactly as it is today. The secrets probe lists exactly the secrets the old `secrets-gate` listed.

### Appendix B: resume gate outputs (WP-04)

```yaml
gate:
  runs-on: ubuntu-latest
  outputs:
    configured: ${{ steps.gate.outputs.configured }}
    count: ${{ steps.check.outputs.count }}
    matrix: ${{ steps.check.outputs.matrix }}
    total_shards: ${{ steps.check.outputs.total_shards }}
  steps:
    - id: gate
      # secrets probe as in Appendix A, with the five secrets today's gate checks
    - uses: actions/checkout@v4
      if: steps.gate.outputs.configured == 'true'
    - uses: pnpm/action-setup@v4
      if: steps.gate.outputs.configured == 'true'
    - uses: actions/setup-node@v4
      if: steps.gate.outputs.configured == 'true'
      with: { node-version: 20, cache: pnpm }
    - run: pnpm install --frozen-lockfile
      if: steps.gate.outputs.configured == 'true'
    - id: check
      if: steps.gate.outputs.configured == 'true'
      run: pnpm exec tsx scripts/ingest-resume-check.ts --limit "${INPUT_LIMIT:-20}" --max-shards 4

resume:
  needs: gate
  if: needs.gate.outputs.configured == 'true' && needs.gate.outputs.count != '0'
  strategy:
    fail-fast: false
    matrix:
      shard: ${{ fromJson(needs.gate.outputs.matrix) }}
```

When `configured` is false the `check` step does not run and its outputs are empty; the `resume` job's `if` is false first, so `fromJson('')` is not evaluated [VERIFY on a dispatch run with an empty secret].
