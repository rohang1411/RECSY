**Date:** October 13, 2026 (America/Los_Angeles)  
**Status:** Investigation complete within the evidence boundaries below; implementation not started.  
**Audited revision:** `ea7b65cf433d890cd3a5995fc2337ed460c269d8`  
**Branch:** `supabase-db-optimisations-changes-rs`  
**Scope:** Current Next.js application, database schema and migrations, scripts, evaluation infrastructure, GitHub workflows, and live Supabase usage/database/access observations. `legacy/` is historical and is excluded from the current runtime audit.  
**Deadline:** Use **November 6, 2026**, as supplied by the user. Supabase's live dashboard says November 7; resolve the discrepancy without extending the earlier deadline. Ship immediate protections promptly, then validate the next billing cycle before November 6.

## 1. What actually exceeded the limit

The incident is an **uncached egress quota breach**, not a database query-count limit or a user-count limit. The RECSY Free organization shows **6.268 GB / 5 GB (125%)**, for the displayed **September 20–October 20, 2026** billing cycle. Its daily chart identifies **5.135 GB on the chart's October 7 date, 100% Shared Pooler Egress**. That single day represents approximately 82% of the displayed cycle total, subject to the dashboard's rounding. The corresponding local load-test artifacts were recorded on **October 6, approximately 6:58–7:54 p.m. PDT** (October 7, 01:58–02:54 UTC).

The strongest supported causal chain is:

1. Four retained 780-request HTTP load-test artifacts target a logical evaluation schema on the **same hosted Supabase database**.
2. Every successful recommendation path reloads an uncached catalog query that joins phones to aspect rows, repeating phone specs and the entire 768-dimensional phone vector in each joined row.
3. PostgreSQL recorded **904 executions / 386,912 rows** for that query in `eval_20261007012955`. Read-only `EXPLAIN VERBOSE` matched its exact query identifier to that schema.
4. The retained evaluation catalog returns **428 rows for 74 phones**, carrying **4,171,427 bytes of repeated vector text plus 366,961 bytes of repeated spec JSON per execution**.
5. Retrieval during the same campaigns also returns chunk vectors as text for MMR; additional probes and snapshot exports add traffic.
6. Supabase records the resulting traffic as shared pooler egress even though the app server is on localhost and the model provider is a controlled test stub.

**Verdict on the user's `/internal` hypothesis:** Internal pages contribute database work and have important access/cache/query problems. However, the observed dominant spike is associated with evaluation/load-test traffic and an amplified recommendation catalog result. A continuous dashboard polling loop was **not found** in the current internal-page implementation. It would be incorrect to identify dashboard telemetry polling as the principal confirmed cause.

**Billing clarification:** The live Usage page explicitly says Free usage is not billed for overages and restrictions can occur. It warns that restricted project requests return HTTP 402. This investigation made no plan, billing, configuration, or production-data changes. Reducing future traffic cannot subtract the 6.268 GB already used. The banner also refers to a previous-cycle breach; the exact historical email-triggering period was not supplied, so this document establishes the current visible breach and does not invent an attribution for every historical notice.

## 4. Design constraints and preserved behavior

1. Keep deterministic seven-factor ranking, hard constraints, neutral defaults for missing aspects, refinement behavior, regional availability/prices and semantic contributions. Optimization must not silently change the candidate universe or choose an arbitrary latest aspect row.
2. Preserve source citations, quote references, RRF/MMR behavior, existing missing-embedding fallback, source diversity, quarantined evidence handling, and review provenance. A cited chunk ID is not proof of factual correctness; this plan adds no quality claims.
3. Preserve historical failed/successful evaluation artifacts and reviewed evidence. Never drop a schema merely because its name starts with `eval_`.
4. Keep private sessions, query logs, operational telemetry, cache prompts and vectors off public bulk endpoints. Authorization must happen before SQL at each server entry point, not only in a parent layout that may render alongside its children.
5. Every cache key must include database identity, schema, region where relevant, corpus/catalog revision, model/methodology versions and query options. Never cache personalized session state globally or share evaluation data with public data.
6. Maintain correctness if caching is cold, unavailable, or stale. Cache errors cannot cause an unlimited refetch storm. Critical exclusions/archival changes need immediate invalidation or a lightweight correctness gate.
7. Prefer existing hosting/cache capabilities and local Postgres/pgvector for tests. Do not add a paid cache, a second cloud vendor, or another production scheduler as a prerequisite.
8. Indexes optimize server work; projection/caching optimize result egress. Shrinking a table or increasing pool size does not solve already-consumed bandwidth.
9. Free-tier operation can be made predictable for a bounded project workload; no design guarantees unlimited traffic, unlimited ingestion, or immunity from provider policy changes.

## 5. Implementation work packages

### Phase A — immediate protection and incident baseline

**Targets:** `scripts/eval-campaign.ts`, `eval-http-load.ts`, `eval-stage.ts`, `eval-benchmark.ts`, `eval-load.ts`, `src/services/eval/preflight.ts`, evaluation routes, `src/app/internal/layout.tsx`, all internal pages, `src/env.ts`, `src/middleware.ts`, `src/app/robots.ts`, `drizzle/rls.sql`, new database migration.

1. Add an explicit DB workload policy shared by CLI and web evaluation: destructive/fault injection, staging-copy creation and load suites default to a **local database**. Checking only `127.0.0.1` for the HTTP URL or checking `DATABASE_SCHEMA` is insufficient.
2. Reject hosted load runs before creating a stage, launching a server, writing benchmark rows, or making model calls. Check normalized database destination plus an explicit configured environment identity; support local Docker/service aliases deliberately. A proxy at localhost must not silently become proof of local quota independence.
3. Allow a deliberately bounded hosted functional smoke only through an explicit mode with a request/result-byte budget and no corpus clone, load sweep or fault injection. Name its shared-host measurement boundary in artifacts. A controlled provider does not remove DB cost.
4. Immediately protect all `/internal/*` pages with a server-side operator session/access capability. Reuse the existing operator-token convention where practical, but use a secure HttpOnly session established through a protected entry point rather than URLs, query strings or a browser-visible permanent secret. When configuration is missing, fail closed. The current production evaluation API already fails closed; preserve that behavior.
5. Add `requireInternalAccess` at each page/route/service boundary before starting promises. Distinguish enabled from authorized. Disable internal navigation prefetch explicitly; add robots exclusions/noindex to internal routes as a supplementary crawler measure. Robots exclusions do not provide authentication.
6. Prepare a migration that enables RLS and revokes unnecessary `anon`/`authenticated` privileges on all private tables, including the eight omissions. Deny public writes. Give regional read data only its intended read policy; protect clients/shares with owner/revocable-token access. Prefer service-only operational tables.
7. Inventory current browser/API reliance before reducing public catalog/corpus grants. No current application Supabase-JS use was found. Replace broad bulk reads with narrowly projected public views or server APIs. Remove vector and `raw_json` access via effective column/table grants; RLS filters rows, not columns. Revoke table-level SELECT before relying on column-only grants. Verify view security and exposed schema configuration.
8. Inventory SECURITY DEFINER functions, executable RPC grants, views, default privileges, and both roles so a newly created table cannot recreate the omission. Preserve a scoped server role and scheduled-worker access; the server's privileged Postgres connection bypasses RLS, so server authorization remains necessary.
9. Record current cycle/usage once outside the production DB. Introduce an emergency maintenance-disable switch and per-run caps; freeze hosted load tests immediately. If needed, reduce scheduled background work while keeping existing catalog reads available. This plan does not itself disable workflows or alter production settings.

**Acceptance:** Unauthorized internal requests start zero app DB statements; no anonymously readable operational rows; anonymous mutations denied in a disposable environment; public browse/phone/recommend operations and scheduled service access still work. Hosted load rejection has zero DB/provider mutations. Never test anonymous writes against production data.

### Phase B — remove the main recommendation payload amplification

**Targets:** `src/services/recommender/catalog.ts`, `run-recommendation.ts`, `match.ts` interfaces if needed, evaluation runners/preflight, `src/services/scorecard/definitions.ts`.

1. Split the current joined result into narrow phone/region data and aspect rows, or aggregate aspect data in SQL into one row per phone. Select phone vectors **once per phone**, never once per aspect. Preserve phones without aspects and use an explicit latest-definition rule with deterministic tie handling. Test older/multiple methodology definitions rather than relying on Map iteration order.
2. Provide a `withSpecEmbeddings`/projection option or separate loader. Preflight, corpus counts, browse/pickers and non-semantic component probes should request IDs/scalars only. Component retrieval preflight currently loads the recommendation catalog unnecessarily; use a narrow active-phone selector instead.
3. Cache reusable phone/aspect/reference data; keep user requirements/session context uncached. Initially retain the existing TypeScript ranker and cosine calculations. This removes amplification with lower behavioral risk than rewriting ranking wholesale in SQL.
4. For public catalog caching, use a backend abstraction. Start with bounded in-process single-flight caching plus the hosting Data Cache for serializable nonprivate data if the deployed Next.js configuration verifies its persistence and item limits. `next.config.ts` currently does not enable Cache Components; do not assume `use cache` works without configuration. [Next.js `unstable_cache` documentation](https://nextjs.org/docs/app/api-reference/functions/unstable_cache) describes caching database results; cookies/headers must be read outside and passed as explicit validated arguments. If using its successor, make that migration explicit and test it.
5. Proposed public catalog freshness: 10-minute TTL plus authenticated invalidation after successful catalog promotion, archive, regional update, scorecard completion and spec-vector backfill. TTL is a starting configuration, not a measured optimum. Invalidate after commit. External GitHub jobs need a protected invalidation endpoint or a revision mechanism; updating a process-local variable in a worker does not invalidate Vercel instances.
6. Version cache entries for DB identity/schema/region/methodology; avoid caching a transaction handle or uncommitted state. Reject unknown regions rather than generating arbitrary cache keys. Use a bounded set of supported regions and immutable cached DTOs.
7. Measure the cold result: today's public vector/spec data once per phone is approximately 0.879 MB, versus approximately 5.396 MB repeated through the join, before other columns. This is a projected improvement to verify after implementation; warm shared-cache hits should send zero catalog-result bytes from Supabase.
8. If cold-instance volume still threatens the budget, move only the semantic similarity calculation into a narrow SQL query returning `{phone_id, similarity}` and cache the remaining compact catalog. Preserve cosine clamping, missing vectors, precision and tie behavior through parity checks before enabling. Do not simply drop semantic ranking.

**Acceptance:** One logical phone row per phone; every vector returned at most once on a cold catalog read; identical eligible candidates/picks/contributions on representative existing fixtures; correct no-aspect/archived/region/refine behavior; no cross-schema cache hits; post-commit invalidation observed across independent server instances.

### Phase C — reduce retrieval vector egress while preserving MMR

**Targets:** `src/services/retrieval/vector.ts`, `fts.ts`, `retriever.ts`, `factory.ts`, `rrf.ts`, `mmr.ts`, retrieval tests, scorecard integration.

1. Keep stage-one vector/FTS queries narrow: chunk/source IDs, scores, citation fields and needed text. Return no raw vector during the initial vector query.
2. After RRF, identify the exact bounded prefix used by MMR (`min(targetResults * 3, fused.length)`). Fetch vectors once for eligible members of that prefix. Initially fetch only members that previously carried a vector-search embedding, preserving the current FTS-only missing-vector penalty. Giving all FTS-only rows new vectors changes ranking and requires a separately reviewed behavior change.
3. Preserve deterministic candidate order and duplicate merging; restore metadata and vector availability precisely. A saved round trip is not worth changed citations or silently altered diversity.
4. Add a bounded immutable corpus-vector cache per phone/revision where measurement justifies it. Initial bounds: a byte cap, TTL and one in-flight fetch per key; revision invalidation on source replacement, source-status changes, quarantine updates and embedding-model changes. Do not serialize complete vectors to client response traces.
5. Reuse retrieval results for identical scorecard aspect queries under the same corpus/model/methodology revision. Query-embedding caching already exists and is bounded; it saves provider calls but **does not cache database retrieval responses**. Add response caching only with complete option keys and a strict byte cap, while keeping benchmark modes explicit about warm/cold cache conditions.
6. Optional later stage: return a bounded pairwise similarity matrix for the MMR prefix, computed in Postgres, rather than raw vectors. pgvector can compute vector-to-vector distance; the current MMR comment claiming Postgres cannot do it should not govern architecture. Benchmark CPU versus egress before choosing this more complex approach.
7. Measure vector/FTS result bytes independently. Cap candidates/result bytes without silently truncating text needed by citation/scorecard validation. Preserve source-quality exclusions and dates.

**Acceptance:** Existing vector/FTS/RRF/MMR ordering and selected citation IDs match the current behavior on a frozen corpus, including FTS-only hits and no-embedding cases. Verify cold and warm payloads; do not disable MMR to produce a smaller result.

### Phase D — make internal observability bounded and demand-driven

**Targets:** `src/services/internal/database-dashboard.ts`, `phone-ingestion-dashboard.ts`, `pipeline-run-monitor.ts`, `llm-usage-monitor.ts`, `pipeline-snapshot.ts`, `phone-evidence.ts`, internal pages/components, evaluation history repository.

1. Load only the selected database tab's details. Return both tab badges from a shared small summary, not both complete diagnostic datasets.
2. Replace `loadCommandCenterIngestionSummary`'s full diagnostic fetch with a summary-specific aggregate/projection. Combine compatible LLM seven-day aggregates rather than scanning `llm_usage_events` separately for each chart; keep the daily Pacific-day boundary explicit.
3. Use a shared cache module with in-flight promise coalescing, bounded keys/bytes, timestamps, failure backoff and maximum stale age. Starting TTLs: command-center metrics 5 minutes, run summaries 1 minute, device evidence 10 minutes, catalog summary 10 minutes. Refresh occurs on authorized demand or existing worker completion; no new frequent cron exists just to keep an unopened dashboard fresh.
4. Each response carries `generatedAt`, freshness/status and warnings. Serve last successful data within an explicit stale bound during dependency failures, visibly labeled stale. Never cache a fallback zero-count dataset as current verified success.
5. Move status/brand/reason/search filters to SQL; paginate diagnostic detail with keyset order such as `(updated_at,id)`. Initial page size 25, maximum 100. Validate filter values/search length. Counts remain separate exact/dated aggregate queries; never derive a global count from a page slice.
6. Fetch quality issues only for displayed candidates with deterministic ordering. The present unordered 300-row limit can omit the reason attached to a displayed candidate; making the UI faster must also fix this correctness problem.
7. Lifecycle currently loads a selected phone, 16 sources, 48 chunks, seven aspects and three sample turns. Preserve these bounds, select only needed columns, and label samples as samples. Its 100-phone selector cap needs pagination/search to avoid silently hiding later phones. Do not replace it with the dormant all-phone 80-chunks-per-phone helper.
8. Add separate authorized drill-down requests for full chunk text, terminal diagnostics and per-run test results. Paginate evaluation results and enforce payload caps; the 30-run history limit alone is insufficient for large JSON.
9. Avoid stacking three independent snapshot services for one badge. Consolidate shared summary reads and cache them. Prefer ordinary indexed aggregate queries at current scale; materialized views or a summary table are justified only if traces show a remaining hot aggregate. Any summary maintenance must cost less than the reads it replaces.
10. If live progress refresh is later desired, make it opt-in, visibility-aware, single-flight and limited to a narrow active-run DTO with backoff. Idle/no active jobs must not poll. The current code does not require such a loop.

**Acceptance:** Navigation/hidden tabs do not start unused detail queries; one cold computation per key under concurrent requests in a process; independent-instance cache behavior tested; lists bounded; no false healthy zeros; 100 authorized reads inside a valid shared TTL do not cause 100 DB recomputations.

| Tiered ingestion daily           | 4 shards × selected tiers; limit 15 per shard          | Keep tier due-date rules; begin with 1–2 workers and an organization-wide run budget |
| Resume daily                     | 4 shards, limit 20 per shard                           | Prioritize only due unresolved failures; share claims/budgets with tiered ingest     |
| Catalog refresh weekly + monthly | Discovery/enrichment/promotion/media/embeddings/report | Keep bounded cadence; skip unchanged entities and redundant media work               |
| Images daily                     | Missing image scans                                    | Run after catalog changes; weekly reconciliation if required                         |
| Keepalive weekly                 | Repository commit only                                 | Not a direct DB query source, but keeps autonomous schedules active                  |

Configured maximums are not actual phone-processing counts. Tier definitions already implement 3.5/7/14-day due intervals, and resume selection already checks cooldowns; preserve these existing protections instead of claiming they are absent.

1. Establish one durable work claim for `(work_type, phone_id)` or `(adapter, canonical_source_url)` with owner, lease expiry, attempts and retry time. Claim a bounded set atomically using `FOR UPDATE SKIP LOCKED`/`UPDATE ... RETURNING`, then commit before external network/model work.
2. Support lease extension, crashed-worker recovery and compare-and-set completion. A transaction-pooler session advisory lock is not a reliable long-lived claim. GitHub concurrency groups currently differ across workflows and cannot establish per-phone exclusion against local/Airflow scripts.
3. Push shard predicates, tiers, due times and limits into selection SQL where stable shard parity can be preserved. A parent roster distributed as a workflow artifact is another option; do not make every shard enumerate the complete candidate set. Bound metadata loading once per job.
4. Use persisted quota/reset-aware cooldowns with jitter and max attempts. Never repeatedly retry Gemini quota exhaustion before the relevant reset; do not use a generic immediate retry to mask a DB connection or Supabase 402 failure.
5. Scorecards become dirty on corpus revision, source visibility, quarantine, methodology or model changes. Avoid seven skip rows for an entirely unchanged phone: emit one phone-run summary with explicit skipped-aspect count, keep real aspect successes/failures, and maintain the existing completeness/fingerprint correctness contract.
6. Keep ingestion's pre-embedding content-hash check: it already prevents unchanged sources from being embedded again. Add canonical URL/version/embedding-model-aware dedupe and conditional updates to stop needless metadata writes. Cross-phone unchanged-source dedupe must still preserve required secondary links.
7. Serialize same-source replacement through a durable lease or a short locked transaction; the existing source lookup before upsert alone does not prove race-free replacement. Reuse chunk IDs for unchanged chunks or maintain historical citation versions so old aspect/chat quotes do not become dangling after delete-and-reinsert.
8. Make per-phone/run limits independent of shard count; include requests, projected returned bytes, growth bytes, retry count and total runtime. Pause maintenance safely at limits with resumable receipts. Report deferred work honestly.
9. Choose GitHub or Airflow as schedule owner if Airflow is activated. Current Airflow DAGs are unscheduled; do not add another live schedule by default.

**Acceptance:** Two workers from different workflows cannot execute the same leased work; expired leases recover; due/cooldown/priority semantics remain correct; no-change scorecard cycles perform no retrieval/model call and write at most one run summary; unchanged ingestion creates no new embeddings/chunks.

### Phase F — cache hygiene, telemetry and retention

**Targets:** `src/services/llm/cache.ts`, `usage.ts`, `rate-limit/consume.ts`, `db/schema.ts`, migrations, new maintenance/pruning script and existing maintenance workflow.

1. Add cache namespace/version/expiry/access metadata and byte-size limits. Use a normal SELECT for cache lookup; aggregate approximate hit statistics off the critical path without an UPDATE for each hit. Label approximate sampled/batched statistics correctly.
2. Fix invalid-entry replacement. Current structured read revalidation can fail, but `onConflictDoNothing` preserves the bad entry. Delete/replace invalid entries safely or use a new versioned key and an upsert; do not keep paying for a refetch against an unusable permanent entry.
3. Keep stable request/model/schema/version keys; add same-process in-flight coalescing so simultaneous misses do not repeat model calls. Do not store complete prompt bodies by default. Retain hash/model/template version and a redacted bounded debug excerpt only when needed. Migrate old `prompt_raw` requirements intentionally.
4. Proposed starting retention, to be encoded in configuration and dry-run reports:

| Data                                           | Proposed policy                                                | Preservation constraint                                                                        |
| ---------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| LLM response cache                             | 30-day expiry, maximum 20 MB; oversized entries bypass storage | Versioning and expiry never return invalid old response                                        |
| Public API rate-limit windows                  | Keep maximum active window + 24 hours                          | Do not remove active windows; add time index if plans justify                                  |
| LLM usage detail                               | 30 days                                                        | Roll up exact day/model/area totals before pruning; retain billing-window reconciliation       |
| Ingest/scorecard successful and skipped detail | 30 days                                                        | Keep compact daily summaries and unresolved/relevant run references                            |
| Failure detail                                 | 90 days, bounded error size                                    | Unresolved work and reviewed incident evidence remain pinned                                   |
| Completed crawl queue                          | 7 days                                                         | Preserve durable source dedupe/terminal status separately                                      |
| Anonymous session/turn/chat data               | Proposed 90 days after inactivity                              | Preserve user-owned/pinned/shared sessions and feedback references; document product retention |
| Benchmark results/evaluation schemas           | Local first; explicit reviewed lifecycle                       | Retain reviewed provenance and required artifacts; no wildcard deletion                        |
| Catalog evidence/raw sources/chunks            | No blanket age-based purge                                     | Corpus/citations are product data, not disposable telemetry                                    |

5. Use a daily bounded maintenance pass, not a delete per request. Delete by indexed time/key ranges in small transactions (e.g. 500 rows), with a runtime cap. Dry-run, target manifest, dependency check and safe restart are mandatory for schema/archive cleanup.
6. Rollup/detail cutovers use idempotent unique keys and transactional watermarks so retries do not double-count. Preserve Pacific-day quota boundaries separately from UTC billing/day grouping. Support failures between rollup and delete.
7. Do not buffer critical usage accounting only in serverless memory: it can disappear at shutdown. Keep durable billing-relevant events; selectively batch disposable operational summaries in workers with explicit flush/receipt behavior.
8. Public API validation should reject malformed/oversized requests before avoidable DB work; retain request-level abuse controls. A rejected valid abusive request must not produce unlimited counter writes. Add edge/local bounded shielding and an atomic DB saturation rule. Do not replace cross-instance enforcement solely with process-local counters.

**Acceptance:** Expired/invalid entries miss and can be refreshed; no write per ordinary cache hit; bytes/entries stay within caps; pruning is idempotent, excludes active/pinned/dependent rows, preserves daily totals, and handles partial failure.

### Phase G — evaluation storage isolation and preservation-safe cleanup

**Targets:** evaluation staging/export scripts, `docs/eval/README.md`, local DB provisioning, archive/cleanup tooling.

1. Provision local PostgreSQL with the needed pgvector/trigram/extensions and apply the same migrations. Existing CI integration jobs already use local service databases; retain that isolation and do not replace them with Supabase secrets.
2. Restore a verified existing catalog/corpus snapshot locally rather than repeatedly downloading it. Keep table hashes, embedding model/dimensions, source revision and corpus provenance. Exclude user logs, tokens and private cache prompts.
3. Register each evaluation environment with source DB identity, created time, expiry, corpus hash, owning campaign and retention/pin state. A failed campaign leaves evidence; the lifecycle manager must still know how to archive it safely.
4. Inventory the two retained hosted schemas and all active sessions/workers, dependencies and known artifacts. Compare existing local archives with current schema/corpus hashes before exporting again. A second full vector export itself costs bandwidth.
5. Produce an exact named cleanup manifest; validate archived rows and provenance, restore to local DB, and verify relevant replay checks before proposing schema removal. Schema drops require a recoverable archive and an explicitly approved execution step; this audit authorizes no deletion. Never execute `DROP SCHEMA` over every matching `eval_*` name.
6. Budget any one-time required export and measure actual billed change. Compression after rows have already left Postgres saves local disk/next-hop traffic, not the Supabase egress already incurred. Prefer a single reusable archive, not repeated corpus snapshots.

**Acceptance:** Future full campaigns consume zero hosted DB workload; hosted copies are removable only after verified local recovery; reviewed evidence and failed attempts remain accessible. ### Phase H — connection, transaction and query-plan engineering

**Targets:** `src/services/db/client.ts`, `connection.ts`, `schema-guard.ts`, `src/app/api/recommend/route.ts`, session handling, schema/migrations, retrieval SQL.

1. Configure pool size by runtime class: start with maximum 2 app connections per serverless process and 1 per worker process, then validate throughput/queueing. Existing `prepare:false` for transaction pooling remains. Aggregate instances × pools × workers against the project connection allowance; tuning per process alone is insufficient.
2. Set driver/connect/statement/lock/idle-in-transaction timeouts appropriate to public reads, operator queries and maintenance. Use actual SQL cancellation or timeout, not only UI promise fallback. Separate workload limits so a legitimate bounded ingestion insert is not cancelled by a dashboard's shorter SLA.
3. Fix recommendation transaction scope with a durable per-session generation lease or optimistic session version: load context and reserve work in a short transaction, release it during model work, then finalize the turn in another short transaction after validating the version/lease. Concurrent turns require explicit queue/retry behavior; do not remove the lock without preserving order and owner checks.
4. Avoid awaiting cache/usage writes on another DB connection while a transaction holds the only connection. A pool reduction alone can create long waits/deadlock-like behavior until transaction scope is fixed. Test the combined changes.
5. Give each workload a static `application_name`/category and external structured metrics without sensitive SQL/prompt parameters. Filter schema guards to required tables/columns and explicit schema; cache guards once per job/deployment revision, invalidated by schema changes.
6. Candidate indexes to evaluate on a local copy, not blindly add:
   - `ingest_runs(phone_id, started_at DESC)` for latest per-phone diagnostics and retry checks.
   - `crawl_queue(phone_id, scheduled_for DESC)` for current per-phone queue lookup; existing status/scheduled index serves due work.
   - Partial/composite scorecard index for `(phone_id, chunk_fingerprint, aspect)` on successful runs if fingerprint plans benefit.
   - Time indexes for expiry/retention where high enough volume justifies them.
   - Candidate filter/keyset indexes driven by actual status/brand/search plans rather than every possible filter combination.
7. Correct the trigram fallback's indexability using a supported trigram operator/prefilter with the intended threshold and keep the explicit strict similarity filter. A threshold change or operator substitution can alter matches; test source IDs/ranking. An existing GIN index does not optimize every `similarity()` predicate automatically.
8. Benchmark exact phone-scoped vector search versus HNSW at current corpus size and compare recall/order. The planner can correctly favor a phone index plus exact distance sort for small subsets. Three retained chunk HNSW indexes and trigram indexes consume substantial space; decide on keeping/removing/rebuilding from actual representative plans, recall and write cost. Do not drop an index solely because `idx_scan=0`.
9. Monitor dead tuples and autovacuum after source replacement. Standard VACUUM reuses space but does not promise to shrink files; VACUUM FULL locks/rewrites and needs maintenance capacity. No routine full vacuum as an egress fix. [Database-size documentation](https://supabase.com/docs/guides/platform/database-size) distinguishes actual data/index storage from WAL/disk usage.

**Acceptance:** Concurrent session ordering preserved without a model-duration row lock; no stranded transaction/pool waits; statement timeout really stops server work; query plans and index decisions recorded with comparable corpus sizes; no retrieval/regional behavior regression.

### 6.2 Meaningful verification

Use a local migrated PostgreSQL/pgvector instance and a frozen verified corpus for regressions/load. Do not rerun a full benchmark against the hosted Free project to validate a bandwidth fix.

- Catalog parity: old/new loaders compared on identical frozen input, multiple aspect-definition versions, no aspects, null vectors, regions, missing/estimated price, archived/upcoming phones and refinement. Assert ranking outputs/contributions and byte/row bounds.
- Retrieval parity: vector/FTS overlap, FTS-only chunks, quarantined chunks, missing vectors, ties, corpus replacement, multiple sources and citation IDs. Verify MMR vector availability remains equivalent.
- Cache tests: concurrent miss coalescing, TTL expiry, failures/stale labels, rejection eviction, bounded keys/bytes, schema/region separation, and worker-triggered post-commit invalidation across instances.
- Access tests: unauthorized server page/route causes zero DB calls; anonymous REST operational/vector/raw reads blocked; writes denied using disposable test rows locally; intended public/server reads succeed.
- DB tests: actual statement cancellation, lease reclaim and duplicate-worker exclusion; same-session concurrent generation ordering; failed finalization recovery; no uncommitted snapshot in caches; no pool starvation from nested cache/usage work.
- Retention tests: dry-run/apply agreement, rolled-up totals, repeated pruning, pinned/unresolved/dependent exclusions, interrupted batches and restored evaluation archives.
- Workload tests: short local request mix with narrow telemetry, byte estimates and cold/warm instance behavior. Budgets reject an oversized run before work starts.

Run focused tests first, then normal repository release checks after implementation. Existing commands:

```powershell
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Formatting must follow the repository's Prettier checks. Integration tests/e2e should use the isolated local database configuration. `pnpm eval:campaign --load` is **not a safe hosted verification command in the current implementation**; run only after the guard exists and the DB identity is local. Do not run `db:reset`, blanket `db:setup`, new staging copies, or cleanup against production during this document review.

## 7. Migration, preservation and rollback

- Add explicit forward migrations and synchronize `db/schema.ts`, setup SQL, tests and documentation. Never rewrite already-applied migration history. Verify RLS/grants for existing databases and fresh installs, including future tables and evaluation schemas.
- Stage catalog projection/cache changes behind a controlled flag; compare results on the local frozen snapshot. Rollback to a narrow uncached loader, not the old amplified hosted query under repeated load.
- Cache rollback invalidates affected namespace/version keys. Failure fallback is bounded and labeled, with single-flight/backoff; it cannot refill from DB on every request indefinitely.
- Access rollback must never restore public operational writes/reads. If an operator access change fails, keep private paths closed while fixing the operator flow.
- Work-claim rollback requires workers stopped and leases reviewed; never let old and new claim mechanisms run concurrently.
- Archive/retention cleanup uses exact target manifests and restore-tested files with hashes. Keep required evidence pinned. Preserve an externally recoverable backup before a production schema drop or irreversible purge.
- Index migrations consider locks, temporary disk, concurrent creation support and rollback cost. Test on local data first; do not bundle large rewrites with the immediate access fix.
- No source/runtime/config/billing/database modifications were performed by this investigation. Only this plan and local diagnostic receipts were created.
