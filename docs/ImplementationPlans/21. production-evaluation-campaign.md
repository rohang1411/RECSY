## Decisions and acceptance contract

- Run fresh-schema integration, security, and fault tests on an isolated PostgreSQL/pgvector instance. Record exact code content hashes, database/schema/corpus snapshots, model, configuration, seed, workload, raw outcomes, failures, and cache behavior. A dirty commit identifier alone is insufficient provenance.
- Repair the actual client/session schema regression using the original migration and ownership model. Verify migration history rather than modifying existing production rows to silence preflight. Test cookie continuity, isolation, malformed inputs, concurrent turns, and error responses through HTTP.
- Treat missing phone, inactive phone, missing corpus, insufficient supporting evidence, and unsupported question as distinct states. Positive quality cohorts require reviewed source evidence; missing-data and unanswerable cases belong to separate failure/abstention cohorts. Coverage failures must be visible and never silently excluded.
- Build source-backed benchmark candidates with immutable source text and hashes, answer facts, required evidence, expected behavior, task category, phone grouping, and split. Generated candidates are not reviewed gold labels. Freeze the final test split before model/ranking tuning; reserve reviewed development data for changes.
- Independently adjudicate answerability, evidence validity, factual support, and completeness. Human review is a pending external input. Automated judgment records model/prompt/version and limitations; it cannot be mislabeled human-reviewed or guaranteed correct.
- Define answer success as sufficient response to the question plus support for every factual claim by the cited evidence. Failures/refusals on answerable cases stay in the denominator. Report retrieval Recall@k, answer success, claim support, completeness, false refusal, abstention, coverage, latency, errors, and observed provider usage separately.
- Compare vector-only, FTS-only, and hybrid on the same frozen questions/corpus/model settings. Use paired differences, grouped uncertainty when questions share phones, and reviewed error analysis. No hybrid-improvement claim without a measured comparison.
- HTTP performance must distinguish controlled-provider plumbing tests from real-provider tests. Use open arrival scheduling, bounded workload, latency/error objectives, warm/cold cache labels, mixed phones/queries, sustained tiers, spikes, and recovery. Record offered, started, dropped, completed, failed, and successful requests. Do not hide NDJSON errors behind HTTP 200.
- Faults include malformed/oversized JSON, unknown/inactive phones, empty corpus, corrupt/unknown citations, prompt injection, provider timeout/429/error, retrieval degradation, DB error, client cancellation, session cross-access, and concurrent persistence. Emit trace IDs and precise operator diagnostics without exposing secrets to public clients.
- Production capacity requires a deployment target, expected demand, provider quota/budget, and representative resource limits. If unavailable, execute a documented local staging campaign and keep production release blocked.
- No claim of a perfect benchmark or absence of all loopholes. Release requires explicit passed gates, reviewer evidence, known limitations, and repeatable raw artifacts.

## Execution sequence

1. Inspect current fixtures, corpus, schema, migration history, environment capabilities, and actual API behavior. Identify data and ownership defects.
2. Restore schema/session compatibility and create isolated staging. Bootstrap from migrations; exercise both routes through real HTTP and DB persistence with deterministic providers explicitly labeled.
3. Add benchmark snapshot/preparation, validation, review/import/freeze, result adjudication, and artifact reporting workflows. Make benchmark coverage and blocked reasons accessible from CLI and portal.
4. Execute functional/fault/security cohorts. Repair observed failures and rerun affected checks. Keep failed first attempts in the evidence record.
5. Execute controlled-provider HTTP load tiers/soak/spike/recovery and bounded live-provider cases within configured quota. Inspect bottlenecks using stage timing and DB telemetry. Establish real-provider capacity only where the run actually includes it.
6. Run source-reviewed held-out Q&A and paired retrieval variants once review/coverage gates pass. Produce the blinded review package and exact remaining review requirements if independent adjudication is unavailable.
7. Update plan 20, context, guide, portal, and operator instructions with actual run results and blockers. Produce readiness verdict and allowable resume wording tied to evidence.
