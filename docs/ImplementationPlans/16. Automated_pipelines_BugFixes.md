# Autonomous Catalog Stabilization & Pipeline Root-Cause Remediation Plan

This implementation plan details the comprehensive architectural fixes for all failed, skipped, and stalled GitHub Actions data pipelines in RECSY. It resolves the inability of the system to detect and ingest newly announced flagships (such as the iPhone 18 Pro / Pro Max launched in September 2026), eliminates fatal database constraint crashes, repairs creator feed discovery, removes false OK/failure reporting in ingestion, and ensures 100% strict adherence to external free-tier quotas (MobileAPI, Gemini, Supabase).

## Analysis of Root Causes & Multi-Perspective Engineering Solutions

### 1. Database Constraint Crash on `scripts/backfill/canonical-keys.ts`

- **Symptom:** Step 6 of `catalog auto` crashed every run on Aug 17, 24, and 31 with:
  `PostgresError: duplicate key value violates unique constraint "phone_identities_type_value_uniq"` on `('recsy_seed', 'apple:iphone-17-pro-max:2025')`.
- **Root Cause:** In `scripts/backfill/canonical-keys.ts`, the upsert used `.onConflictDoUpdate({ target: [phoneIdentities.sourceKey, phoneIdentities.externalId], ... })`. But the table also enforces a unique index on `(identityType, externalId)`. When a phone was previously recorded by `recsy_catalog`, attempting to insert as `recsy_seed` did not match the target `[sourceKey, externalId]` because `sourceKey` differed. Postgres attempted an insert, causing error 23505 and crashing Step 6, which aborted the workflow before Step 7 (`catalog:auto`) could ever run.
- **Senior Staff Engineer Perspective:** An identity mapping in an entity-resolution system must resolve by business identity `(identityType, externalId)` first. We check existing identities by either `(identityType, externalId)` or `(sourceKey, externalId)`. If existing, update the `phoneId`, `sourceKey`, and `lastSeenAt`; if absent, insert with `.onConflictDoNothing()`.

### 2. Wikidata Discovery Blindness (Missing iPhone 18 & Modern Devices)

- **Symptom:** The live SPARQL query against Wikidata returned only 1 device (`Light Phone III`) across 2025–2026. Live inspection confirmed iPhone 18 exists in Wikidata as entity `Q139556016`, but was completely filtered out.
- **Root Cause:**
  1. Class filtering: `VALUES ?class { wd:Q17517 wd:Q22645 wd:Q19723444 }` omitted `wd:Q19723451` ("smartphone model"), which Wikidata uses for modern iPhone lines.
  2. Date property omission: Apple launch entities on Wikidata use `wdt:P6949` ("announcement date") upon launch before `wdt:P571` (inception) or `wdt:P577` (publication) are backfilled weeks later.
- **Senior AI & Data Architect Perspective:** Expand the SPARQL query in `src/services/catalog/adapters/wikidata.ts` to include `wd:Q19723451`, support subclass traversal `wdt:P31/wdt:P279*`, and coalesce announcement date `wdt:P6949` with publication/inception dates.

### 3. Quarantine Deadlock on Newly Announced Flagships (`missing_spec_field`)

- **Symptom:** 41 out of 65 entries in `catalog_candidates` were quarantined with `missing_spec_field`. Zero new phones reached the active catalog.
- **Root Cause:** `spec-project.ts` strictly required all core fields (including battery `capacity_mah` and `ram_gb`) at discovery time. However, OEMs (especially Apple) never disclose exact battery mAh or RAM capacity during launch keynote events; these are only revealed days/weeks later via teardowns. Treating missing battery/RAM as an unrecoverable failure permanently blocks newly announced flagships.
- **Senior Software Architect Perspective:** In `src/services/catalog/spec-project.ts` and `candidate-policy.ts`, introduce an "announced/flagship-staged" relaxation: For Tier-1 brands (Apple, Samsung, Google) with valid chipset, display, storage, and release year, allow promotion with placeholder/estimated spec tags while queueing `catalog-enrich-gsmarena.ts` and Wikipedia infobox scraping to fill real teardown values once available.

### 4. Creator-Watch Dead Feeds (404) & Passive Architecture

- **Symptom:** 4 of 6 active creator channels in `creator_profiles` returned HTTP 404. Furthermore, `creator-watch` only looked for videos matching existing phones in `phones`, making it incapable of discovering new phones.
- **Root Cause:** Stale channel IDs in `creator_profiles`. Architectural passivity where creator feeds were consumers rather than discovery scouts.
- **Senior AI Engineer Perspective:**
  1. Fix channel IDs in `creator_profiles` (MKBHD, Mrwhosetheboss, Dave2D, etc.).
  2. Add an uncataloged title-matcher in `src/services/ingest/adapters/youtube-channel.ts`: When top-tier tech reviewers release a video titled "iPhone 18 Pro Review" or "Pixel 10 Impressions", extract the candidate device name, verify brand against Tier-1 roster, and stage it into `catalog_candidates` with source `'creator_watch'`. This provides day-zero discovery even if Wikidata is slow.

### 5. Ingest Pipelines False OK & False Failures

- **Symptom:** `ingest (resume)` reported "Success" with 0 chunks written. `ingest (tiered)` failed on cold-tier Sundays because `--fail-on-zero-success` threw an error when all articles matched existing hashes.
- **Root Cause:** Inability of the CLI exit code to distinguish between idempotency (`unchanged-content`, 0 new chunks needed) and failure (0 sources discovered due to network/parsing errors).
- **Senior Software Architect Perspective:** In `scripts/ingest-auto.ts`, classify results into `written`, `unchanged`, and `failed`. Record `status = 'unchanged'` in `ingest_runs`. Remove `--fail-on-zero-success` from `ingest-tiered.yml`. A shard where existing content is verified fresh should succeed cleanly.

### 6. MobileAPI Rate-Limiting & Quota Discipline

- **Symptom:** Occasional 429 errors when requests fired in bursts, or complete dormancy because weekly runs were allocated 0 requests.
- **Senior Architect Fix:** Enforce a hard 13,000ms pause between consecutive MobileAPI requests. Allocate a weekly micro-budget (5 requests max) in `catalog-refresh.yml` to check the latest releases, preserving the free-tier quota (50 reqs/month).

### 7. GitHub Actions Inactivity Keep-Alive

- **Symptom:** GitHub Actions crons shut down automatically after 60 days of commit inactivity.
- **Fix:** Add a lightweight scheduled keep-alive workflow (`.github/workflows/keepalive.yml`) that runs weekly and touches a small timestamp file or uses the GitHub API to keep workflows active.
