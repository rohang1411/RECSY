Other interpretation limits: benchmark status `success` means the suite finished, not all cases passed; warnings must remain visible. RAG exceptions/missing phones are excluded from the successful-score arrays, so report coverage/failure counts alongside means. Bootstrap confidence intervals describe variation in the selected fixture sample; they do not fix a wrong measurement definition, a deterministic mock, biased relevance labels or data leakage. A second model or majority vote does not automatically eliminate evaluator bias. No significance result should be cited merely because a statistical helper exists.

## Tests actually run

`pnpm exec vitest run src/services/eval/metrics.test.ts src/services/eval/dialog-state.test.ts`: **23 tests passed across 2 files**. These tests validate their encoded expectations, not the stronger claims in the documentation.

Additional direct counterexamples, executed with the existing functions from a probe saved under this analysis's evidence folder:

- An unrelated claim pointing to an existing chunk received `citePrec = 1`, while support recall was 0.
- An answer with zero citations received `citePrec = 1`, `phantomRate = 0`.
- “$99” against evidence “$999” passed the numerical check.
- Matching one of two expected state fields received `jgaScore = 0.5`, rather than an exact-match failure score.
- Zero recommendations received budget, dealbreaker, platform and overall constraint success.

These are concrete measurement defects, not proof that the recommender itself returns those problematic outputs in normal use. The distinction matters: the model may work well, but these evaluators cannot establish the advertised quality.

## Required evaluation repair before a result enters the resume

1. Persist code revision, dataset hash, catalog snapshot/count, provider/model for each pipeline stage, prompt version, run timestamp, sample count and actual token usage. Separate stub and live tracks explicitly.
2. Fix exact-state scoring, denominators for applicable retention/mutation/reset checks, answerability and empty-output handling. Add regression tests for the counterexamples above.
3. Assess recommendations against independent constraints and a held-out relevance set. Preserve MAUT agreement as an explicitly named consistency metric, alongside an independent quality measure.
4. Evaluate answers against the exact retrieved evidence used to generate them. Separately measure citation-ID validity, claim support, unsupported answers and appropriate abstention. Include failures in coverage reporting.
5. Run unseen paraphrases and adversarial edits; keep test fixtures separate from prompts/parser development. Report per-session aggregates where turns share state.
6. For performance, measure full-request latency and success at a stated concurrency, sustained duration and dataset size. Separate retrieval-only and generation-inclusive timings, warm/cold paths and cache effects. Actual pool measurements must replace the arithmetic proxy.
7. Select the resume metric based on project purpose: helping users find suitable phones and trust evidence-backed answers. A comprehensible result such as correctly honoring budget/brand changes across a defined held-out conversation set is more relevant than an impressive but ungrounded QPS number.

No fixed future numerical target is promised. The resume currently reports implemented evaluation coverage, not a repaired score that has not yet been measured. Implementation changes belong in the RECSY project task; this request's deliverable is the resume/evidence analysis, so no project source was silently modified.
